### FK-44 · Moodle worksheet import is unreachable from where marking starts

- **Why it's a defect, not a preference:** importing a worksheet is a **pre-marking** action — it pre-seeds the class list before any student is marked. The placement contradicts the workflow the feature was designed for: a new marker reaches "Student" first, types a name by hand, and never learns the import exists.
- **Evidence:** O — read on `origin/main` (the planning worktree is ~5 weeks stale; merge-base `1af58be` 2026-06-11, so read `main`, not this branch). Section order + rail link set verified by grep of `id="sec-*"` and `href="#sec-*"`.

  1. Add a rail link for the Cohort section so it is reachable at all, matching the existing rail-link markup and the FK-28/FK-29 `aria-current` + scroll-spy behaviour.

- **Risks & mitigations:** low. (1) Rail crowding on narrow viewports → check the rail at mobile widths before merge. (2) Two triggers for one modal could confuse → both call the same handler, so behaviour is identical by construction.
- **Constraint added 2026-07-24 (for FK-48):** both entry points must carry a **single shared hook** — one common class or `data-fk-moodle` attribute on the rail link and the `#sec-student` control — so FK-48 can hide them with one conditional instead of hunting ad-hoc markup. ### FK-45 · Let markers choose where exported files are saved (D6 slice 1)
- **Summary:** Every file FK produces — scorer JSON, student Excel, cohort Excel, Moodle worksheet, snippet CSV — is written with an anchor `download` attribute (`builder.html:1224`, `scorer.html:3561`, `scorer.html:4297`), so it lands in the browser's default download folder with no way to pick a destination. A lecturer keeping course files in a OneDrive or shared course folder has to move every file by hand after each save. The only workaround today is the browser-level "Ask where to save each file" setting, which is not FK's to control and which markers do not know about.
- **Evidence:** O — verified on `origin/main`: `showSaveFilePicker` / `showDirectoryPicker` appear **nowhere** in `scorer.html`, `builder.html`, `upload.html`, `convert.html`, `js/shared.js`, or `js/converter.js`. Storage is localStorage plus anchor downloads, exactly as README's storage model describes.
- **Relationship to D6:** `fk-decisions.md` D6 (signed 2026-05-16, both sides) specifies a full folder-adapter backend — `showDirectoryPicker()`, per-entity JSON, `kitchen-config.json`, ETag-on-load conflict handling, permission-renewal banner. That is the v1.1 P0 design and it is **unimplemented**. This card is deliberately **not** that: it is the smallest slice that solves the lecturer-visible problem without taking on handles, permission renewal, or autosave.
- **Proposed slice:** route the existing download helpers through a single `saveFile(blob, filename)` shim that tries `window.showSaveFilePicker()` (native Save-As dialog: the marker picks the folder, and the browser remembers the last-used location) and falls back to the current anchor-download path when the API is absent (Firefox and Safari have no support) or when the user cancels. One helper, called from the existing call sites; no change to what any file contains.
- **Dependencies:** none hard. Does **not** block on D6 and does not pre-empt it — if the full folder backend is built later, this shim is the natural place it plugs in. **Feature worktree/branch, not here.**
- **Test strategy:** unit-test the shim's fallback branch (picker absent → anchor path; picker throws `AbortError` → no file written, no error surfaced). Existing export tests must stay green unchanged, which is the real assurance that file *contents* did not move.
- **Risks & mitigations:** (1) Browser split — Firefox/Safari markers keep exactly today's behaviour, so the fallback is the common path, not an edge case; do not write copy that promises a folder picker to everyone. (2) A cancelled dialog must be a silent no-op, not an error toast. (3) `showSaveFilePicker` requires a user gesture — all these call sites are already click handlers, so this holds, but assert it in review.
- **DoD:** a marker on Chrome or Edge can send a scorer JSON and a cohort Excel straight to a folder of their choosing; Firefox/Safari behaviour unchanged; cancel is a no-op; export contents byte-identical to before; jest green.
- **Column:** Safe to implement now. **Priority:** P2. **Effort:** S–M. **Phase:** D6 slice 1.
- **Answers:** the "save a scorer somewhere other than FK's default" gap raised 2026-07-24. Until this ships, the manual documents the browser setting as the only route.

### FK-48 · Per-scorer Moodle declaration (`CONFIG.moodleEnabled`)
- **Summary:** Let the person building a scorer declare whether that assessment is delivered through Moodle. When it is not, the Moodle entry points (the rail link and the `#sec-student` control from FK-44, plus the canonical controls in `#sec-cohort`) are **hidden**, so a marker in a non-Moodle context never sees them.
- **Framing correction (matters for the copy):** the Moodle round trip never contacts Moodle. It is CSV file exchange (`js/moodle-worksheet.js`), so the controls **work fine** on a machine with no Moodle in sight — they are merely irrelevant. This is a relevance filter, not a capability gate, and no UI string should say "unavailable" or imply the feature is broken.
- **Where the flag lives — `CONFIG`, not the settings blob.** O: `getSetting`/`setSetting` (`scorer.html:5012–5026`) read and write a single `SA_SCORER_SETTINGS_V1` object in localStorage, which is **device-global**, not per-scorer, and is not part of the scorer JSON. `clearTutorBetweenStudents` and the FK-12 cohort-consistency toggle both live there. Reusing that pattern would switch Moodle off for **every scorer on the device**, breaking the lecturer who has one Moodle paper and one that is not. `FK_MOD_EXPORT_OPTINS` (`js/moderation-optin.js:19`) is the same device-local shape. So neither existing toggle is the precedent; the flag belongs in the scorer config object.
- **Consequence, and it is the right one:** in `CONFIG`, the flag travels with the JSON export, so a marking team sharing one scorer inherits the declaration. An assessment either is or is not delivered through Moodle, and that is true for everyone marking it. A recipient at a different institution can flip it, which is why it must stay editable after import.
- **Back-compat, no migration:** treat `CONFIG.moodleEnabled !== false` as enabled. Existing saved scorers and existing exported JSON files have no such field and keep today's behaviour untouched.
- **Where it is set:** builder step 6 (Settings and save), beside the late-penalty block, which is where assessment-shape decisions already live. Also editable afterwards from the scorer settings panel, but that editor **writes through to `CONFIG`**, not to `SA_SCORER_SETTINGS_V1`. New scorers present it checked with a one-line explanation; the deliberate choice is opting *out*.
- **Hide, do not disable.** Disabled-with-tooltip is correct when an in-session action can unlock the control, which is exactly why moderation export uses it (mark 15 students and it turns on). Nothing a marker does in-session changes Moodle availability, so a permanently greyed button is noise: it invites a click, explains itself only on hover (unreachable on touch, unreliable to a screen reader), and works against FK-44's purpose of decluttering the marking path. Discoverability is preserved because the toggle is visible where the assessment is configured.
- **Dependencies:** **FK-44 first** — it introduces the second entry point, and its shared-hook constraint is what keeps this card's render change to one conditional. **Feature worktree/branch, not here.**
- **Test strategy:** unit-test the back-compat predicate across `undefined` / `true` / `false`. Static-HTML guard that both FK-44 entry points and the `#sec-cohort` controls carry the shared hook. Round-trip test: build with the flag off, export JSON, re-import, flag survives. Confirm the device settings blob is **not** written by this feature.
- **Risks & mitigations:** (1) Hiding a working feature from someone who needed it — mitigated by the builder prompt and the post-import editor. (2) Scope creep into a general "which integrations does this scorer use" framework; resist, this is one boolean. (3) A hidden section must not leave a dangling rail link or an empty `#sec-cohort` heading; assert both.
- **Edge case that must be handled — stranded mid-round-trip.** A marker imports a Moodle worksheet, marks half the cohort, then the flag is turned off (by them, or by re-importing a shared scorer JSON that has it off). A blanket hide would remove **Export Moodle worksheet…** while a cohort seeded from Moodle is still in flight, with no way to finish the round trip and no explanation. Resolve one of two ways: (a) keep the export control visible whenever the open cohort contains Moodle-imported records, regardless of the flag, which makes the flag govern *entry* to the workflow rather than exit from it; or (b) warn at the point of switching off that a Moodle-seeded cohort is open, and require confirmation. Prefer (a) — it needs no new copy, cannot strand anyone, and matches the read that this is a relevance filter: the workflow is plainly relevant if you are already inside it. Whichever is chosen, add a test for the half-marked-cohort case.
- **DoD:** a scorer built with Moodle declared off shows no Moodle entry point anywhere; one built with it on is unchanged from post-FK-44 behaviour; flag survives JSON export and import; existing scorers unaffected without migration; device settings blob untouched; jest green; axe 0. Manual part 6 gains a sentence about the toggle as part of this card.
- **Column:** Safe to implement now (after FK-44). **Priority:** P2. **Effort:** M. **Phase:** FK-19 / FK-44 follow-on.
- **Sequencing:** FK-44 → FK-48 → FK-46, so the manual publishes describing the finished behaviour once rather than being rewritten twice.

### FK-47 · Hard-wire a documentation review gate for user-facing behaviour changes
- **Rationale:** A manual is only worth publishing if it cannot silently rot. FK already has the failure mode on record: the FK-11 doc-drift residual (fixed in PR #41) and the two drift items listed under FK-46 all reached `main` because nothing forced a documentation check when behaviour changed.
- **Mechanism (proposed, needs owner sign-off):** a documentation-impact step that fires on the pull request rather than on a calendar. Three parts. (1) A **surface-to-section map** in `MANUAL-MAINTENANCE.md` naming, for each documented feature, the files that own it, so "did I touch a documented surface?" is a lookup rather than a judgement call. (2) A **pull-request checklist line** — does this change alter anything in the map, and if so, which manual sections were updated in the same PR. (3) A **CI guard** in the existing static-assertion style: if a PR's diff touches a mapped file, require either a matching change under `docs/` or an explicit `docs-impact: none` line in the PR body.

Documentation accuracy is not observable that way, and a weekly reminder that the manual "might" be stale creates noise the silence contract is designed to avoid. The moment of truth is the change itself.
- **Dependencies:** FK-46 (nothing to protect until the manual is published). The CI guard reuses the FK-23 workflow wiring.
- **Risks:** an unconditional gate becomes a rubber stamp. Mitigation: scope the map narrowly to genuinely user-visible surfaces, and make `docs-impact: none` a legitimate, low-friction answer.
- **DoD:** map written and agreed; checklist line in the PR template; guard green on a PR that touches a mapped file with docs, and red on one without; process documented in `MANUAL-MAINTENANCE.md`.
- **Column:** Backlog (blocked by FK-46). **Priority:** P2. **Effort:** S–M.
