### FK-54 · "Rubric has changed" warning fires on students who were never marked
- **Summary:** Opening an unmarked cohort record raises an amber toast reading "Rubric has changed since this record was saved — review each row." The claim is untrue for a Moodle-imported placeholder: nothing changed, and the record was never saved *from* marking — `buildCohortImport` seeds identity only, deliberately writing no `scoreResult` and no grades (`js/moodle-worksheet.js:279–281`). The warning is a signal about rubric drift being spent on a record that has no rubric history at all.
- **Cause:** `loadCohortRecordIntoSession` fires the toast whenever `savedGrades.length !== config.criteria.length` (`scorer.html:3299–3301`). An unmarked placeholder has `savedGrades.length === 0` against a rubric of N criteria, so the inequality always holds and the toast always fires.
- **Evidence:** O — observed in a real browser 2026-07-27 while verifying FK-53 against `origin/main` @ `c49c148`, captured via a MutationObserver on the toast container. Confirmed pre-existing: the same branch fires today on the FK-27 auto-open path, which lands the marker on the first imported student straight after `mwCommit()`. Not introduced by FK-53.
- **Why it matters now — corrected 2026-07-27.** The escalation needs **FK-53 *and* FK-55**, not FK-53 alone. As first written this card said FK-53 (PR #110) turned a once-per-import annoyance into once-per-student. That was only true in normal mode: FK-53's control was unreachable in Focus mode, where no advancing happened at all, so no per-student repetition occurred there. **FK-55 (PR [#111](https://github.com/stephendmann/feedback-kitchen/pull/111)) is what makes it once-per-student everywhere.** The defect itself, its cause and its fix are unchanged and were re-confirmed in the FK-55 Focus-mode run; only the severity attribution was wrong. It still holds that a warning crying wolf on every student is worse than no warning, because it trains markers to dismiss the one case where the rubric genuinely did change mid-cohort — the FK-11 / FK-25 signal this toast exists to carry.
- **Deliberately not fixed in FK-53 or FK-55.** The fix touches shipped FK-11/FK-25-adjacent behaviour and belongs in its own change with its own test, rather than widening a card whose whole argument is that it is the smallest safe slice. Declined twice on that basis, both times at owner's instruction.
- **▶ NEXT ACTIVE product card (2026-07-27).** Carded that morning as the next task after FK-53 shipped, then displaced the same day by FK-55 — a P1 correctness gap, since FK-53's control turned out to be unreachable in Focus mode and the feature did not meet its own DoD on a supported path. Nothing about this card was wrong; it was out-prioritised by a defect in the feature that motivated it. **FK-55 merged (PR #111), so this returns to the front of the queue.** Both halves of its premise now hold on `main`: the control exists and advances through the roster in every mode, so the toast repeats once per student wherever a marker works.
- **Proposed fix (smallest slice):** guard the branch on the record having *some* saved marking — `savedGrades.length && savedGrades.length !== config.criteria.length` — so a never-marked record stays silent while a genuinely drifted one still warns. Check whether `FKMoodle.recordHasMarks(rec)` is the better predicate than a raw length test, since it is already the codebase's one definition of marked-ness and would keep this consistent with the export and with FK-53's `nextUnmarkedKey`.
- **Dependencies:** none hard. Independent of PR #110 — the defective line is on `main` today — but the payoff lands with it. **Feature worktree/branch, not here.**
- **Test strategy:** unit or static guard that an unmarked placeholder opens without the toast, and that a record saved against a shorter/longer rubric still raises it. Regression: FK-27's post-import auto-open path stays green.
- **Risks & mitigations:** (1) Over-suppression — a record marked against a rubric that has since *gained* criteria has `savedGrades.length` non-zero, so it still warns; verify with a test rather than by reading. (2) The message may also be wrong for a partially-marked record; check the copy against what it is actually detecting before rewording. (3) Do not fold in the wider FK-11/FK-25 drift-badge behaviour — this is one predicate, not a review of the drift model.
- **DoD:** opening an unmarked placeholder raises no rubric-change toast; a genuine rubric change still does; FK-27 import path unchanged; jest green; axe 0.

### FK-48 · Per-scorer Moodle declaration (`CONFIG.moodleEnabled`)
- **Summary:** Let the person building a scorer declare whether that assessment is delivered through Moodle. When it is not, the Moodle entry points (the rail link and the `#sec-student` control from FK-44, plus the canonical controls in `#sec-cohort`) are **hidden**, so a marker in a non-Moodle context never sees them.
- **Framing correction (matters for the copy):** the Moodle round trip never contacts Moodle. It is CSV file exchange (`js/moodle-worksheet.js`), so the controls **work fine** on a machine with no Moodle in sight — they are merely irrelevant. This is a relevance filter, not a capability gate, and no UI string should say "unavailable" or imply the feature is broken.
- **Where the flag lives — `CONFIG`, not the settings blob.** O: `getSetting`/`setSetting` (`scorer.html:5012–5026`) read and write a single `SA_SCORER_SETTINGS_V1` object in localStorage, which is **device-global**, not per-scorer, and is not part of the scorer JSON. `clearTutorBetweenStudents` and the FK-12 cohort-consistency toggle both live there. Reusing that pattern would switch Moodle off for **every scorer on the device**, breaking the lecturer who has one Moodle paper and one that is not. `FK_MOD_EXPORT_OPTINS` (`js/moderation-optin.js:19`) is the same device-local shape. So neither existing toggle is the precedent; the flag belongs in the scorer config object.
- **Consequence, and it is the right one:** in `CONFIG`, the flag travels with the JSON export, so a marking team sharing one scorer inherits the declaration. An assessment either is or is not delivered through Moodle, and that is true for everyone marking it. A recipient at a different institution can flip it, which is why it must stay editable after import.
- **Back-compat, no migration:** treat `CONFIG.moodleEnabled !== false` as enabled. Existing saved scorers and existing exported JSON files have no such field and keep today's behaviour untouched.
- **Where it is set:** builder step 6 (Settings and save), beside the late-penalty block, which is where assessment-shape decisions already live. Also editable afterwards from the scorer settings panel, but that editor **writes through to `CONFIG`**, not to `SA_SCORER_SETTINGS_V1`. New scorers present it checked with a one-line explanation; the deliberate choice is opting *out*.
- **Product shape confirmed by owner 2026-07-24** (chat, this session). Decisions signed: flag in `CONFIG`; default **on** for new scorers; hide (not disable) when off; export path stays visible while the open cohort holds Moodle-imported records. Default-on rationale, in weight order: (1) wrong-default costs are asymmetric — a wrong "on" is two irrelevant controls, a wrong "off" hides the feature from a Moodle marker entirely, recreating the FK-44 defect per scorer; (2) absent-reads-as-enabled means legacy scorers all show Moodle, so default-off would fork behaviour by scorer age within one team; (3) the known user base skews Moodle. Revisit only if issue #89 analytics show a majority non-Moodle audience. Note the predicate/default separation: `!== false` handles back-compat on its own, so the new-scorer default can be flipped later without any migration.
- **UX spec (agreed):** one checkbox in step 6, sibling to the existing `enable-late-penalties` toggle (same show/hide-a-behaviour pattern). Label: "This assessment is marked in Moodle"; helper line: "Shows the Moodle worksheet import and export tools in the scorer. You can change this later in scorer settings." Sentence case per canon §7. Post-build: the same checkbox in the Scorer settings panel, writing through to `CONFIG`. Explicitly rejected: an LMS dropdown (integrations framework with one integration), step-1 placement (question before context), a first-run prompt in the scorer (interrupts marking), and any "enable integration"-style wording (capability framing for what is a relevance filter).
- **Stranded-round-trip predicate is already cheap:** `buildCohortImport` stamps `source: 'moodle-worksheet'` (+ `moodleIdentifier`) on every imported record (`js/moodle-worksheet.js:279–280`), so "open cohort contains Moodle-imported records" is a one-line check over existing data — nothing new is written at import time.
- **Hide, do not disable.** Disabled-with-tooltip is correct when an in-session action can unlock the control, which is exactly why moderation export uses it (mark 15 students and it turns on). Nothing a marker does in-session changes Moodle availability, so a permanently greyed button is noise: it invites a click, explains itself only on hover (unreachable on touch, unreliable to a screen reader), and works against FK-44's purpose of decluttering the marking path. Discoverability is preserved because the toggle is visible where the assessment is configured.
- **Dependencies:** **FK-44 first** — shipped 2026-07-24 (commit `24b5373`), and it has already laid the hook this card needs. The three selectors are live: `[data-fk-moodle="entry"]`, `[data-fk-moodle="import"]`, `[data-fk-moodle="export"]`. Hide `entry` + `import` when the scorer declares it is not marked in Moodle; leave `export` visible whenever the open cohort holds records with `source === 'moodle-worksheet'`. **Feature worktree/branch, not here.**
- **Test strategy:** unit-test the back-compat predicate across `undefined` / `true` / `false`. Static-HTML guard that both FK-44 entry points and the `#sec-cohort` controls carry the shared hook. Round-trip test: build with the flag off, export JSON, re-import, flag survives. Confirm the device settings blob is **not** written by this feature.
- **Risks & mitigations:** (1) Hiding a working feature from someone who needed it — mitigated by the builder prompt and the post-import editor. (2) Scope creep into a general "which integrations does this scorer use" framework; resist, this is one boolean. (3) A hidden section must not leave a dangling rail link or an empty `#sec-cohort` heading; assert both.
- **Edge case that must be handled — stranded mid-round-trip.** A marker imports a Moodle worksheet, marks half the cohort, then the flag is turned off (by them, or by re-importing a shared scorer JSON that has it off). A blanket hide would remove **Export Moodle worksheet…** while a cohort seeded from Moodle is still in flight, with no way to finish the round trip and no explanation. Resolve one of two ways: (a) keep the export control visible whenever the open cohort contains Moodle-imported records, regardless of the flag, which makes the flag govern *entry* to the workflow rather than exit from it; or (b) warn at the point of switching off that a Moodle-seeded cohort is open, and require confirmation. Prefer (a) — it needs no new copy, cannot strand anyone, and matches the read that this is a relevance filter: the workflow is plainly relevant if you are already inside it. Whichever is chosen, add a test for the half-marked-cohort case.
- **DoD:** a scorer built with Moodle declared off shows no Moodle entry point anywhere; one built with it on is unchanged from post-FK-44 behaviour; flag survives JSON export and import; existing scorers unaffected without migration; device settings blob untouched; jest green; axe 0. Manual part 6 gains a sentence about the toggle as part of this card.
- **Column:** Safe to implement now (after FK-44). **Priority:** P2. **Effort:** M. **Phase:** FK-19 / FK-44 follow-on.
- **Sequencing:** FK-44 → FK-48 → FK-46, so the manual publishes describing the finished behaviour once rather than being rewritten twice.

### FK-49 · Three shipped controls carry `hidden` but render visible (`.btn` beats `.hidden`)
- **Summary:** `.btn { display: inline-flex }` outranks Tailwind's `.hidden { display: none }`, so adding the `hidden` class to a `.btn`-classed element applies the class and hides nothing. Three shipped controls are affected on `main` right now: `btn-insights` ("Cohort Insights"), `btn-modexport-run` ("Export for Moderation") and `btn-modexport-disable` ("Disable moderation export"). All three carry `hidden` in the served markup and compute to `display: flex`.
- **Evidence:** O — found during FK-48 runtime verification 2026-07-24, then confirmed **on `main` independently of that branch** by auditing `[...document.querySelectorAll('.hidden')].filter(e => e.classList.contains('btn'))` and reading computed display on each. Live on the deployed site.
- **Impact:** this defeats the FK-08 / INS-2 moderation lifecycle split, which is explicitly "configure (always visible, self-relabels when enabled) / run / disable (both hidden until opted in)". Markers see "Export for Moderation" and "Disable moderation export" on a paper that has never been opted in, and "Cohort Insights" before a cohort is large enough for it. Not a data leak (the export itself is still gated, and the blocked path shows the "Moderation Export blocked" dialog), so this is misleading UI rather than a privacy failure. It also means any future `hidden`-based hiding of a `.btn` will silently fail the same way.
- **This is FK-16's hazard, realised.** The FK-16 card already records "Tailwind utilities silently fail on `.btn`-classed elements" as a proven cascade problem. This is the first confirmed case of it shipping to users rather than being caught in development.
- **Options:** (a) raise `.hidden`'s specificity for these cases, e.g. a `.btn.hidden { display: none !important }` rule in `shared.css`, which fixes every present and future occurrence in one line and is the smallest change; (b) convert the affected call sites to inline `style.display`, which is what FK-48 did for its own controls but leaves the trap in place for the next author; (c) fold into FK-16's broader consolidation, which is correct long-term but leaves three visible controls wrong in the meantime. Prefer (a) plus a test.
- **Dependencies:** none. Independent of FK-48 (that card sidesteps the hazard for its own three controls but deliberately does not fix these).
- **Test strategy:** a static guard is not enough, because the markup looks correct: the class *is* present. Needs a runtime assertion (the a11y battery already drives a real browser) that no element carrying `hidden` has a computed display other than `none`. That single check would have caught all three and prevents recurrence anywhere on the page.
- **Risks:** low, but verify that nothing currently depends on those controls being visible-despite-hidden. `refreshModExportUI` and the insights gating both *intend* them hidden, so fixing the cascade restores the designed behaviour rather than changing it. Screenshot-diff the cohort action row before and after.
- **DoD:** the three controls are genuinely hidden in their default state; a runtime guard asserts `hidden` implies `display: none` across the page; FK-08's lifecycle split behaves as specified; axe 0; jest green.
- **Column:** In progress (PR #94). **Priority:** P2 (user-visible on production, but not a data or privacy fault). **Effort:** S.
- **UPDATE 2026-07-24 — scope grew twice during implementation (PR #94).** (1) A **fourth** leak found: `#framework-label-chip` sets `display: inline-flex` from an **ID** selector, which outranks `.hidden` outright. Different mechanism from the `.btn` source-order tie, same defect class. It renders an empty pill beside "Rubric scores" whenever no marking framework is set. (2) The `.btn.hidden` fix appeared to do nothing, which uncovered the real problem: **`css/shared.css` has been committed truncated since before FK-30 (PR #54, 2026-06-15)**. Its final `@media (min-width: 1100px)` block ends with a selector, no declarations and no closing braces, leaving the file 2 braces short, so the parser drops everything from there to end-of-file. Two consequences: the 1100px footer variant has never applied, and **any rule appended to this stylesheet silently does nothing** — the invisible-failure mode that made the first fix look wrong. Braces now balanced 37/37; parsed rules 30 → 32.
- **Rejected:** `.hidden { display: none !important }`. It would beat the responsive variants and break every `hidden md:block` element in the app. Scoped overrides used instead, after verifying no `.btn` relies on a responsive un-hide.
- **Guard shipped:** runtime check in `bbp-a11y-tests.mjs` (any element carrying `hidden` whose computed display is not `none`), skipping responsive-variant elements — without that filter it reports 19 false positives from the legitimate `hidden md:block` idiom.
